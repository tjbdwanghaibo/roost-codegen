# roost-codegen 全功能使用手册与用例

本文覆盖 `roost` 项目命令和所有独立生成器。业务项目默认由 Makefile/CI 调用 `@latest` 的 `roost`，独立命令主要用于调试或只采用部分框架能力的仓库。

```bash
go install github.com/tjbdwanghaibo/roost-codegen/cmd/roost@latest
roost help
```

生成器共同原则：输入是唯一事实来源；生成文件带 `Code generated` 标识；内容未变化时不改 mtime；标记、ID、签名或 tag 不合法时 fail-fast；不要手改生成文件。框架更新策略默认是 `latest`，但 `go.mod/go.sum` 始终保存一次解析得到的具体版本，根 `go.mod` 不保留 `replace`。

## 0. 内置帮助系统

安装完成后运行：

```bash
roost help                  # 能力目录
roost help <capability>     # 指定能力的配置与例子
roost help all              # 全部专题
roost <command> --help      # 上下文帮助
```

可查询的 capability：`project`、`versions`、`generate`、`add`、`mods`、`dao`、`entity`、`nest`、`protocol`、`cfggen`、`tablegen`、`eventgen`、`attribute`、`webroute`、`errcode`、`saga`、`replication`、`config`、`id`、`format`、`deploy`。专题输出统一包含用途、命令、配置/marker 和可复制的最小示例。

```bash
roost help dao
roost help replication
roost project deps --help
roost add saga --help
```

生成项目的更新命令：

```bash
make project-upgrade # 使用最新 codegen 升级受控工程模板
make deps-update  # 只按 versions 策略更新 core、kit、skill
make roost-up     # 执行 GOWORK=off go get -u ./... 和 go mod tidy
make codegen-up   # 更新本机安装的 roost CLI
```

`project-upgrade` 会通过 `@latest` 执行 `roost project upgrade`，并把 core、kit、skill、codegen 四个策略设为 `latest`。`roost-up` 后应执行 `make ci`，确认依赖 API 与生成代码仍兼容。

## 1. 项目生成器：roost project

### 1.1 创建项目

```bash
roost project new planet \
  -module example.com/planet \
  -out ./planet \
  -services game,gate \
  -mods configdata,etcd,redis,mongo,nats,sync,remote_entity,checkpoint,nestwal,nest \
  -features protocol,config,entity,nest,event,dao,errcode
```

主要产物：`roost.yaml`、main/bootstrap/Service、配置、Makefile、CI、开发 compose，以及 Shell、Docker、Kubernetes 生产部署模板。Secret 示例和业务文件归应用所有，后续 sync 不覆盖；带生成标识的装配文件由生成器管理。

### 1.2 同步、预览和诊断

```bash
roost project diff                 # 只显示将发生的变化
roost project sync                 # 按 roost.yaml 更新生成文件
roost project doctor               # 含生成物新鲜度检查
roost project doctor -strict=false # 只检查结构、版本和配置
roost project doctor -json         # CI/平台读取 JSON
```

同步时会重新解析 core、kit、skill 的最新版本；也可以只更新依赖：

```bash
roost project sync
roost project deps
```

三个模块在一条 `go get` 中作为直接依赖联合更新，随后自动执行 `GOWORK=off go mod tidy`。因此依赖图选择最高版本，kit/skill 不会把 core 或 kit 降到旧版本。依赖更新失败会恢复原 `go.mod/go.sum`。若需提高最低版本，可用 `project upgrade -core vX.Y.Z -kit vX.Y.Z -skill vX.Y.Z -codegen vX.Y.Z`；core、kit、skill 的明确值是 MVS 下限而不是上限，且必须满足 codegen 的兼容门槛。`latest` 始终直接通过静态版本门禁。

### 1.3 升级旧项目模板

旧项目尚无 `make project-upgrade` 时，在项目根目录执行：

```bash
go run github.com/tjbdwanghaibo/roost-codegen/cmd/roost@latest project upgrade --root . --dry-run -core latest -kit latest -skill latest -codegen latest
go run github.com/tjbdwanghaibo/roost-codegen/cmd/roost@latest project upgrade --root . -core latest -kit latest -skill latest -codegen latest
```

第一条命令只预览受控文件差异；第二条更新 `roost.yaml` 版本策略、codegen 管理的模板和框架依赖。旧的生成 Makefile 会获得 `project-upgrade`、`roost-up`、`codegen-up` 等当前目标。升级可重复执行；业务文件不会覆盖，没有 `Code generated by roost-codegen` 标识的自定义 Makefile 会直接报冲突。

## 2. 统一生成流水线：roost generate

默认顺序为 DAO → Event → Errcode → Protocol → Entity → Nest → Attribute → Config → WebRoute，避免后一个生成器读取旧产物。

```bash
roost generate                  # 全量增量生成
roost generate --changed        # 只运行受 git 变更影响的生成器
roost generate --dry-run        # 打印计划，不写文件
roost generate --check          # 在临时副本生成并检查仓库是否最新
roost generate --force          # 强制重写生成物
```

CI 推荐：

```bash
roost generate --check
roost config check --service game --production \
  --file configs/service/config.game.prod.yaml
roost id check
roost format check
go test ./...
```

## 3. 业务骨架：roost add

支持 `service|mod|module|protocol|entity|component|event|table|dao|webroute|errcode|saga`。

```bash
roost add service world -mods etcd,redis,mongo,nats,nestwal,nest
roost add mod saga -service game
roost add module inventory
roost add protocol use_item -group game
roost add entity player
roost add component inventory
roost add event player_level_up
roost add table monster
roost add dao player
roost add webroute gm_query
roost add errcode item_not_found
roost add saga cross_server_trade -service game -steps reserve,deduct,deliver
```

需要编号的类型默认从 `roost.yaml` 的 ID 空间分配；`-id` 可显式指定，`-group` 选择协议分组。骨架只提供正确目录和最小签名，业务字段、Entity 与 DAO 绑定、Saga handler 仍需开发者补充。

## 4. DAO 生成器

命令：

```bash
go run github.com/tjbdwanghaibo/roost-codegen/cmd/dao@v1.7.0 \
  -def ./db/def -out ./db -pkg db
```

定义：

```go
package dbdef

//cube:dao coll=players db=game dbscope=sid
type PlayerDao struct {
    Name      string
    Level     int32
    LastLogin int64             `dao:"persist"`
    Session   string            `dao:"nopersist,sync"`
    Runtime   int64             `dao:"-"`
    Items     map[int64]int32   `dao:"persist,sync,map=fast"`
    Tags      map[string]string `dao:"persist,map=sharded"`
}
```

字段 tag：

| tag | 持久化 | 客户端同步 | 说明 |
| --- | --- | --- | --- |
| 无 tag | 是 | 是 | 默认 |
| `persist` | 是 | 否 | 仅保存 |
| `nopersist,sync` | 否 | 是 | 临时但需同步 |
| `-` | 否 | 否 | 完全排除 |
| `map=fast` | 按其它标记 | 按其它标记 | 高吞吐 map |
| `map=sharded` | 按其它标记 | 按其它标记 | 分片并发 map |

生成后的存储字段全部私有，业务读写使用方法：

```go
dao := db.NewPlayerDao()
dao.SetName("alice")
name := dao.Name()
dao.SetLevel(10)
dao.SetItems(10001, 3)
count, ok := dao.GetItems(10001)
dao.RangeItems(func(itemID int64, count int32) bool { return true })
dao.DelItems(10001)
```

生成器同时产出 dirty mask、undo、字段级 patch、BSON marshal/unmarshal、schema migration、rollback snapshot、CommitParticipant、`RestorePersisted` 和 `DirtyTracker()`。业务不能访问 `tracker`、存储字段或 map 内部引用；Entity generator 也只通过 `DirtyTracker()` 取得 checkpoint tracker。

Redis DAO 使用 `//cube:redisdao`，生成类型化 Get/Set/Delete 包装；具体 marker 参数与 fail-fast 规则见根 README 的 DAO 章节。

## 5. Entity 生成器

命令：

```bash
go run github.com/tjbdwanghaibo/roost-codegen/cmd/entity@v1.7.0 \
  -dir ./game/entities/player
```

定义示例：

```go
package player

import "github.com/tjbdwanghaibo/cube-core/entity"

const (
    EntityCategoryPlayer entity.EntityCategory = 1
    EntityKindPlayer     entity.EntityKind = 1000
    CompTypeBag          entity.ComponentType = 2000
)

var _ = func() struct{} {
    entity.MustRegisterEntityKindCategory(EntityKindPlayer, EntityCategoryPlayer)
    return struct{}{}
}()

//cube:entity id=1000 entityKind=EntityKindPlayer
type Player struct {
    *entity.EntityBase
    entity.ComponentManager
    entity.DaoManager

    bag *BagComponent `comp:"CompTypeBag"`
    dao *PlayerDao    `dao:"players"`
}
```

产物 `<entity>_gen_wire.go` 包含 factory、Base/Component/DAO getter、组件/DAO 装配、Snapshot、RemoveSnapshot、生命周期 hook；`remote=managed` 时还生成 Remote Entity commit participant。`sync=true` 可同时声明 `syncTopic`、`syncPacker`、`subjectPacker`。

DAO 必须实现 codegen 生成的标准方法，尤其是 `DirtyTracker() *checkpoint.DirtyTracker`。v1.7.0 起 Entity 不再直接访问 `dao.Tracker` 字段，因此与私有 DAO 存储兼容。

## 6. Nest handler 生成器

```bash
go run github.com/tjbdwanghaibo/roost-codegen/cmd/nest@v1.7.0 \
  -dir ./game -sender=true
```

```go
//roost:nest rollback=undo durability=strict
func handlerTransfer(from IPlayerEntity, to IPlayerEntity, itemID int64, count int32) error {
    // 进入前两个 Entity 已按全局顺序加锁
    return nil
}

//roost:nest sync rollback=state durability=async
func handlerQuery(player IPlayerEntity) (PlayerView, error) { return PlayerView{}, nil }
```

| 选项 | 值 | 含义 |
| --- | --- | --- |
| `rollback` | `state`、`undo` | 全状态快照或生成 setter 的逆操作 |
| `durability` | `memory`、`async`、`strict` | 内存、WAL admission、严格提交 |
| `sync` | flag | 生成同步 Sender |

第一个或多个 Entity 接口参数是锁目标；`[]IEntity` 表示实体组。生成 `<source>_nest_gen.go`、sender/syncsender 和 bootstrap 注册代码。

Remote read 可放在请求 struct：

```go
type QueryRequest struct {
    Target entity.RemoteViewRef `remote:"view.PlayerViewMapSnapshot,consistency=monotonic,required"`
}
```

生成 `TargetPlayer()`/`MustTargetPlayer()` 访问器。可选一致性、scope、tenant、policy、allow-stale、min-version 和 cache TTL 均在生成期校验。

## 7. Protocol 生成器

```bash
go run github.com/tjbdwanghaibo/roost-codegen/cmd/protocol@v1.7.0 \
  -def ./protocol/def \
  -proto ./protocol/proto -pb ./protocol/pb \
  -msgid ./protocol/msgid -bind ./protocol/player_bind \
  -handlers ./game/protocol_handlers \
  -manifest ./protocol/protocol_manifest.json
```

定义：

```go
//go:build protocoldef

package protocoldef

//roost:proto package=planet.protocol go_package=example.com/planet/protocol/pb;pb

type PingRequest struct { ClientTime int64 `pb:"1"` }
type PingResponse struct { ServerTime int64 `pb:"1"` }
type Notice struct { Text string `pb:"1"` }

//cube:protocol group=game handler=player
type GameProtocol interface {
    //cube:msg id=10001 tags=local
    Ping(PingRequest) PingResponse       // request/response
    //cube:msg id=10002
    Upload(PingRequest)                  // client push
    //cube:msg id=10003
    Notify() Notice                      // server notify
}
```

产物包含 `.proto`、pb Go、msgid、player binding、handler、robot registry 和协议 manifest。ID 全局查重；字段 `pb:"N"` 不得复用。反向生成：

```bash
go run .../cmd/protocol@v1.7.0 \
  -reverse-proto ./third_party/game.proto \
  -reverse-out ./protocol/def/imported -reverse-package imported
```

## 8. cfggen：YAML schema 先行配置

```bash
go run github.com/tjbdwanghaibo/roost-codegen/cmd/cfggen@v1.7.0 \
  -meta ./configs/schema/cfg.yaml -out ./configs/generated -pkg generated
```

```yaml
package: generated
beans:
  - name: DropItem
    fields:
      - {name: item_id, type: int32}
      - {name: count, type: int32}
tables:
  - name: monster
    key: id
    fields:
      - {name: id, type: int32}
      - {name: scene_id, type: int32, index: true}
      - {name: drop_id, type: int32, ref: drop, required: true}
globals:
  - name: world
    fields:
      - {name: width, type: int32}
```

```go
generated.MustRegisterGeneratedConfigData(configdata.DefaultRegistry())
snap := configdata.ActiveSnapshot()

sameScene := generated.MonsterBySceneID(snap, 7)

```

完整类型系统、bean、ref/index/required/skipempty 和校验规则见 [CFGGEN_META.zh-CN.md](CFGGEN_META.zh-CN.md)。

## 9. tablegen：Go metadata + CSV

```go
//cube:table name=monster file=monster.csv json=monster.json key=ID
type Monster struct {
    ID      int32  `csv:"id" json:"id" title:"ID" required:"true" unique:"true"`
    Name    string `csv:"name" json:"name" title:"名称" required:"true"`
    SceneID int32  `csv:"scene_id" json:"scene_id" ref:"scene"`
}

//cube:object name=world file=world.csv json=world.json
type World struct { Width int32 `csv:"width" json:"width"` }
```

```bash
go run .../cmd/tablegen@v1.7.0 \
  -meta ./configs/schema \
  -out ./configs/generated -pkg generated \
  -csv-template ./configs/template

go run .../cmd/tablegen@v1.7.0 \
  -meta ./configs/schema -csv ./configs/csv -json ./configs/data

go run .../cmd/tablegen@v1.7.0 \
  -meta ./configs/schema -json ./configs/data -check
```

CSV 前四行依次为字段名、标题、类型和规则；转换会校验 required、数字格式等并生成 `_manifest.json`。`cfggen` 适合 YAML schema 单一来源，`tablegen` 适合已有 Go 类型和策划 CSV 流程，两者通常二选一。

## 10. eventgen

事件定义中所有 `Event` 前缀 struct 都会进入生成：

```go
package eventdef

type EventPlayerLevelUp struct {
    PlayerID int64
    Level    int32
}
```

接收者只写约定方法：

```go
func (p *Player) DealEventPlayerLevelUp(e *event.EventPlayerLevelUp) {}
```

```bash
go run .../cmd/eventgen@v1.7.0 \
  -def ./event/def -out ./event -pkg event \
  -game ./game -eventpkg example.com/planet/event
```

产物包括事件定义、EventType、`Type()` 实现和接收者订阅/分发代码。方法名与参数类型不匹配会生成期失败。

## 11. attribute

```go
//cube:attribute index=1 max=64
type PlayerProfile struct {
    HP     int64 `attr:"hp"`
    Attack int64 `attr:"attack"`
    Power  int64 `attr:"power"`
}

// 下划线方法表示派生属性公式；参数名对应输入字段。
func (p *PlayerProfile) _Power(Attack int64, HP int64) int64 {
    return Attack*2 + HP/10
}
```

```bash
go run .../cmd/attribute@v1.7.0 -dir ./game/attribute
```

生成属性 ID/mask、metadata、类型化 setter、dirty mask、派生属性 Update、clone/snapshot 和容器访问器。所在包需提供框架约定的 `AttrID`、`AttrValue`、`AttributeMeta`、`AttributeProfile`、`Snapshot`、`Container`、`Selector` 类型。派生公式出现环、未知字段或重复输出时生成失败。

## 12. webroute

```go
//cube:web method=POST path=/gm/player body=json
func queryPlayer(ctx context.Context, svc *Service, req QueryRequest) (QueryResponse, error) {
    return QueryResponse{}, nil
}

//cube:web method=POST path=/webhook body=raw
func webhook(ctx context.Context, svc *Service, req webroute.RawRequest) (Ack, error) {
    return Ack{}, nil
}
```

```bash
go run .../cmd/webroute@v1.7.0 -dir ./service/web
```

生成 `RegisterRoutes`。JSON 模式只接受一个完整 JSON 文档并统一返回 400 解码错误；raw 模式保留原始 body。是否拒绝未知 JSON 字段由 `cube-core/webroute.DecodeJSON` 的版本契约决定。重复 method/path、非法 body mode 或 handler 签名直接失败。

## 14. 配置、格式和生产门禁

```bash
roost config check --service game
roost config check --service game --production \
  --file configs/service/config.game.prod.yaml
roost format check
```

当前 production 静态检查会解析 YAML、要求 `sid`，并拒绝 `CHANGE_ME`、localhost/127.0.0.1 和 `dev-` 前缀值。项目生成的生产模板会另外给出 Mongo replica set、Redis AOF/WAL 和 JetStream 副本建议，但 `config check` 不会替代这些组件自身的拓扑探测；发布环境仍需启动探针和故障演练。

### 14.1 独立生成器参数速查

| 命令 | 输入参数 | 输出参数 | 其它参数 |
| --- | --- | --- | --- |
| `dao` | `-def`（默认 `./db/def`） | `-out`（默认 `./db`）、`-pkg` | `-force` |
| `entity` | `-dir`（默认当前目录或 `GOFILE` 所在目录） | `-output`（默认每个 Entity 一个 wire 文件） | `-force` |
| `nest` | `-dir`（默认 `.`） | 按源文件生成 | `-sender`、`-force` |
| `protocol` | `-def` | `-proto`、`-pb`、`-msgid`、`-bind`、`-handlers`、`-robot-protocol`、`-manifest` | `-reverse-proto`、`-reverse-out`、`-reverse-package`、`-force` |
| `cfggen` | `-meta`（默认 `./configs/schema/cfg.yaml`） | `-out`（默认 `./cfg`）、`-pkg` | 无 |
| `tablegen` | `-meta` | `-out`、`-pkg`、`-csv-template`、`-json` | `-csv`、`-check`、`-force` |
| `eventgen` | `-def`、`-game` | `-out`、`-pkg`、`-eventpkg` | `-force` |
| `attribute` | `-dir` | `-output` | `-force` |
| `webroute` | `-dir` | 按源目录生成 | `-force` |
| `errcode` | `-root` | `-out` | 无 |

任何独立命令均可加 `-h` 查看当前版本的权威默认值。生产工程优先把这些参数写进 `roost.yaml` 后使用 `roost generate`，避免开发机与 CI 命令漂移。

## 15. 常见问题

- **entity 生成代码访问 `dao.Tracker` 编译失败**：使用 v1.7.0 重新生成；新模板调用 `DirtyTracker()`。DAO 与 Entity 必须由同一代 codegen 重新生成。
- **`go mod tidy` 删除 skill**：新项目的 `internal/frameworkdeps/generated.go` 用类型别名固定 skill module。
- **生成后 CI 有 diff**：先运行 `roost generate`，确认没有手改生成文件；CI 用 `--check`。
- **输出目录无法确定 package**：先放一个非生成 `.go` 文件，或使用 `-pkg`。
- **标记没有生效**：标记必须紧邻目标声明，孤儿标记会报错；不要放在生成文件中。
- **直接修改 DAO 字段不再编译**：这是预期保护，改用生成 getter/mutator；不得为了兼容重新导出存储字段。
- **跨平台 golden 误报**：v1.7.0 只规范化 CRLF/LF，其他模板内容仍完整比较。

## 16. 推荐的日常闭环

```bash
roost add dao player
roost add entity player
# 补全 DAO 字段、Entity 的 dao/component tag 和 Nest handler
roost generate
roost project doctor
make ci
git diff --check
```

代码生成只消除一致性敏感的样板，不代替领域建模。Entity 边界、事务 durability、Remote read level、Saga 补偿和协议兼容仍必须由业务显式决定并经过评审。
